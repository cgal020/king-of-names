# Decisions

One line per meaningful decision or deviation from the brief, newest last.

- 2026-10-06: All provider accounts (Supabase, Vercel, GitHub, OpenAI, Anthropic, Mapbox) are owned by Cameron.
- 2026-10-06: Region is Singapore (Supabase `ap-southeast-1`, Vercel `sin1`): the best single compromise between Dubai, Australia and Thailand.
- 2026-10-06: Next.js 16 calls its middleware file `proxy.ts`; Supabase session refresh lives there.
- 2026-10-06: Supabase's new "publishable" and "secret" keys go into the brief's `NEXT_PUBLIC_SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` variables; legacy anon and service_role keys also work.
- 2026-10-06: No Docker on the dev machine, so development uses a hosted Supabase dev project; production is a separate project.
- 2026-10-06: Profiles are created by a trigger on `auth.users` from sign-up metadata, so a user can never exist without a profile.
- 2026-10-06: `captures` gains `geocode` (jsonb) and `recorded_timezone` columns so a draft can be reopened after a closed tab without re-billing Mapbox.
- 2026-10-06: `people` gains a generated `search_text` column (name, notes, where met, place, city) with a trigram index; search is `ilike` on that column.
- 2026-10-06: The RLS test runs against the dev project (`npm run test:integration`), separate from the offline unit tests (`npm test`).
- 2026-10-06: Login accepts username or email; a server route looks up the email for a username and returns a generic error on failure.
- 2026-10-06: Sign-up skips email confirmation because invite codes already gate access. Password reset email goes through a custom SMTP provider (Resend by default); Supabase's built-in email only reaches project team members.
- 2026-10-06: Reverse geocoding uses Mapbox `permanent=true` because results are stored. It has no free tier ($5 per 1,000 lookups at the time of writing) and needs a card on Cameron's Mapbox account.
- 2026-10-06: Rate limit (60 captures per hour per user) counts the user's `captures` rows from the last hour. No Redis.
- 2026-10-06: Recording duration is reported by the device and checked against the 90 s cap plus a 10 MB size cap; the server does not decode audio.
- 2026-10-06: Audio is uploaded with its base MIME type (for example `audio/webm`, without `;codecs=opus`) to match the bucket's allowed types.
- 2026-10-06: Placeholder name "PeopleMap" with a muted green accent, both set in `lib/config.ts`.
- 2026-10-06: Built a clickable mockup of Capture, Review, People, Profile, Map and Settings with sample data (`lib/mock/`) before milestones 2 to 7, at Ann's request, to review look and flow. Screens and components are the real ones; milestones 2 to 7 replace the sample data with Supabase and delete `lib/mock/`.
- 2026-10-06: Design direction "quiet utility" (Apple Notes, Things), avoid corporate-CRM feel; recorded in PRODUCT.md.
- 2026-10-06: System font stack instead of a web font: native feel on iPhone and Android, nothing to download, works offline.
- 2026-10-06: Optional fields (phone, birthday, follow-up, company, email) stay hidden behind "+" chips until they have a value, so review is a glance rather than a form.
- 2026-10-07: Photos added to Phase 1 (approved by Ann): the person (profile picture), their business card, and the moment or place. New `photos` table and private `photos` bucket. Estimated 5 to 7 extra hours on the 36-hour budget.
- 2026-10-07: Photo geotag rule: a photo just taken in the app gets the phone's GPS; a library photo only gets the GPS saved inside it (often stripped by iOS and Android), otherwise "No location". The phone's current position is never stamped on an old photo.
- 2026-10-07: Photos are re-encoded to JPEG (max 2048 px) in the browser before upload, which strips all EXIF; the location we keep lives in database columns.
- 2026-10-07: Captures and photos link to people through same-user composite foreign keys, so a row can never point at another account's person even though row level security allows inserting your own row.
- 2026-10-07: Playwright (from the brief's test stack) runs against the installed Chrome (`channel: "chrome"`) to avoid a browser download; `npm run screenshots` captures every screen for design reviews.
- 2026-10-07: Business card scanning, card QR codes and Ask AI added to the mockup at Ann's request. Real-build estimates on top of the 36 hours: card photo reading +3–4 h, QR scanning +4–6 h, Ask AI +8–12 h (photos +5–7 h). Together about +20–29 h; needs Cameron's sign-off before the real build.
- 2026-10-07: QR codes are read with the browser's BarcodeDetector where it exists (Chrome on Android) and jsQR otherwise (iPhone Safari has none); jsQR loads only on the scan screen. vCard, MECARD, tel:, mailto:, WhatsApp and other links are parsed locally; links to digital cards and LinkedIn are saved, never fetched or scraped.
- 2026-10-07: Card details merge into the voice-note draft with printed values winning for phone, email, company and role; the card's name replaces the spoken one only when that was missing or uncertain. Fields from the card are labelled "From card" on review.
- 2026-10-07: Ask AI lives in the People search box (no fourth tab): questions are detected as you type, with suggested questions and a voice option. The real version will be Claude with tools that query only the signed-in user's people, citing every person it names.
- 2026-10-07: Privacy note updated: business card photos and Ask AI questions (with the notes needed to answer them) go to Anthropic; photos of people never go to an AI.
- 2026-10-07: Photos store the timezone they were taken in, so times show as local to the place.
- 2026-10-07: Tagging added at Ann's request: a relationship (Business, Personal or Both) and free "how they could help" tags, with starter tags Investor, Client, Partner, Supplier, Connector, Advisor, Talent, Friend. Stored on `people` as `relationship` and `tags text[]` (GIN index; tags included in search). The AI suggests both from the voice note and the user confirms on review. Real-build estimate +3–4 h.
- 2026-10-07: "Both" counts as business and as personal in filters and Ask AI. Tags are deduplicated case-insensitively and stored as typed with a capital first letter.
- 2026-10-07: Ask AI gets its own tab (Capture, People, Ask, Map), chosen by Ann for visibility. This deviates from the brief's three-tab bar. The Ask tab keeps a thread of questions and answers with suggested questions, typing and voice; a question typed into People search offers "Ask AI" and opens it on the Ask tab. The question is handed over in memory, not in the URL, so it never reaches server logs.
- 2026-10-07: Market research report (docs/research/market-research-2026-10.md, 256 sources) published as a private page for Ann.
- 2026-10-07: From the research: adding a photo of a person ("Them") first asks for confirmation that they agreed, citing UAE Cybercrime Law Art. 44; card and place photos need no prompt. Face recognition is ruled out.
- 2026-10-07: From the research: most digital-card QR codes hold only a profile link. The scanner recognises Blinq, Popl, HiHello, Linq, Wave, V1CE, Tapt, Mobilo and Haystack links and LINE profiles, saves them, and offers "Photograph the card" to get the details; the link and the card's details are merged.
- 2026-10-07: Recommended features added to the mockup at Ann's request ("proceed with your recommendations"): Save to contacts (vCard 3.0 with a "met at … on …" note, photo, tags; iOS "Create New Contact" hint), a "met again" meeting timeline on profiles, Coming up (birthdays and follow-ups due within six weeks, overdue follow-ups first) on People, trip mode on the Map, My card (your own vCard QR, works offline), contact import (.vcf files and the Android Contact Picker, with a preview), a one-time AI consent sheet before the first recording, and a privacy pledge in Settings. Rough real-build estimates: 2, 3–4, 2, 3–4, 1–2, 3–4 and 2 hours.
- 2026-10-07: Meetings: each confirmed capture is a meeting with a person; the person's first meeting is when they were added. Profiles show every meeting, newest first, and recording from a profile adds one instead of overwriting notes.
- 2026-10-07: Claude and ChatGPT connector: a read-only MCP server at /api/mcp (mcp-handler 2 with @modelcontextprotocol/server 2) offering search_people, get_person, coming_up and people_near. In the mockup it serves sample data in development only (404 in production). Real build: Supabase Auth's OAuth 2.1 server as the authorization server, withMcpAuth verifying access tokens, queries through the user's token so row level security applies, off by default with a Settings switch and a list of connected assistants. Estimate +8–12 h.
- 2026-10-07: The AI consent answer is kept in the browser in the mockup; the real app stores it on the user's profile.
- 2026-10-07: Real build started on the parts that need no accounts. AI pipeline (lib/ai, lib/geo, lib/pipeline): OpenAI `gpt-transcribe` with a context prompt plus keyword hints built from the user's own names, companies, places and tags (passed through the request body, as OpenAI documents); Claude Haiku 4.5 (`EXTRACTION_MODEL=claude-haiku-4-5`, the brief's "small fast model") with structured outputs (`messages.parse` + Zod) for extraction and business-card reading; Mapbox Geocoding v6 reverse with `permanent=true`.
- 2026-10-07: Extraction also suggests relationship and up to four tags, preferring the user's existing tags. Model output is re-validated after parsing: impossible dates and birthdays become null, phones keep digits and a leading + only, tags are deduplicated, a missing name is always low confidence.
- 2026-10-07: The transcript is wrapped in <transcript> tags marked as untrusted data, and any closing tag inside it is stripped. Error text saved on a capture names only the failed step and error type, never note content.
- 2026-10-07: Geocoding runs in parallel with transcription to stay within the 10-second target. Mapbox v6 has no venues, so the stored place is the neighbourhood or street and the venue comes from what the user said.
- 2026-10-07: The extraction system prompt is shorter than Haiku's minimum cacheable prefix, so it isn't marked for prompt caching.
- 2026-10-07: `npm run eval:extraction` runs the 13 sample transcripts against the real model (costs a few cents; needs keys). Vitest configs for unit, integration and eval tests are separate, so each runs only its own files.
- 2026-10-07: Installable app and offline (milestone 8, real build). Manifest opens on Capture in standalone mode, with Home Screen shortcuts for Record a note (`/capture?record=1`, starts recording at once), Scan a card and Ask. `npm run icons` renders every icon (192, 512, maskable 512, Apple 180) from one pin-on-green design, so they never drift apart.
- 2026-10-07: Hand-written service worker (`public/sw.js`), no Workbox or Serwist dependency. It keeps only the shell: Capture, the offline page, and the build files those two pages reference, precached at install so Capture works offline even if it was never opened while the worker was in control. Each online visit to Capture refreshes the offline copy and drops build files from earlier deploys. Pages always come from the network; offline, Capture opens from the copy and other pages show the offline screen. API routes, React Server Component payloads and other pages are never cached. It registers in production only and is served with no-cache so updates arrive on the next visit.
- 2026-10-07: Real-build rule that follows from that: Capture's server-rendered HTML must hold no personal data (drafts and the "needs review" strip load in the browser), because that HTML is kept in the cache. Sign-out clears the caches and, if notes are waiting to send, warns before discarding them.
- 2026-10-07: Recording uses MediaRecorder with the format chosen at runtime: WebM/Opus where supported (Chrome, Android), MP4 otherwise (iPhone Safari), never Ogg; 32 kbps, stopped automatically at 90 seconds. A level meter comes from the live audio, and the screen is kept awake while recording. Where a page can't record (plain HTTP on a LAN address), the mockup simulates instead.
- 2026-10-07: Capture tries the upload first; a failure or a 15-second timeout puts the note in the IndexedDB queue as "waiting to send". `navigator.onLine` is only a shortcut, because a weak signal often reports online while uploads fail. Retries happen when the app opens, comes back online or becomes visible, and every 30 seconds while notes wait and the app is on screen, since a recovering weak signal fires no online event. Still a simple retry, with no Background Sync (brief; iPhone has none). The browser is asked to keep the storage through clean-ups.
- 2026-10-07: Queue runs never overlap (the app opening and coming online can fire together), so a note is never uploaded twice from the phone. `POST /api/captures` will take the capture id from the phone and ignore a repeat (`on conflict (id) do nothing`), so a retry after a timeout that did reach the server can't create a second capture.
- 2026-10-07: Install help (brief §8): a one-line prompt on Capture in phone browsers (not on desktop, not once installed). "How" opens an instruction screen. On iPhone it gives the Share → Add to Home Screen steps, covering Safari's ⋯ menu and "Open as Web App". On Android it uses Chrome's install prompt when offered, otherwise the menu steps. Dismissal is remembered. Screens under 720 px tall tighten the Capture heading so the record button stays in view with Safari's toolbars showing.
- 2026-10-07: `npm run check:pwa` runs these behaviours in Chrome with a simulated microphone (11 checks on the dev server; 15 with `--prod` against a production build, including the service worker offline with Chrome's own cache cleared). Still to do on real phones: standalone mode on iPhone Safari and Android Chrome, especially microphone and location permissions (brief §8).
- 2026-10-08: The product is called King of Names (Ann); "PeopleMap" was the brief’s placeholder. Renamed in the app name, manifest, connector, docs and package name. The browser storage keys and the offline queue database were renamed too (`king-of-names:` prefix), which is free now because nobody uses the app yet. Check on a real iPhone that “King of Names” fits as the Home Screen label; if it is cut off, give `shortName` in `lib/config.ts` a shorter form.
- 2026-10-08: Real GPS stamp (brief §7.1, research rec. 1). Recording starts `watchPosition` (high accuracy) and keeps the most accurate reading, stopping once it is within 25 m. When recording stops without any fix yet, it waits up to 3 more seconds, then the note goes without a location and the city is set on review. A refused permission doesn't wait at all. The note carries lat, lng and accuracy. Photos and card scans ask for location only when the picture was just taken, starting the request when the camera opens so it is ready by the time the photo is. The Map's Near me, Add person and Met again still use the sample position until the database exists (milestones 3 and 7).
- 2026-10-08: The place name on the recording screen ("Dubai Marina · within 12 m") comes from `POST /api/geocode`, which uses Mapbox's temporary geocoding: it is free up to 100,000 lookups a month, and allowed because the result is only shown. The place that is stored is still looked up with permanent geocoding during processing. Coordinates go in the request body, not the URL, so they stay out of server logs. The route is development-only until sign-in exists; without a Mapbox token the chip says "Location saved".
- 2026-10-08: Upload checks for `POST /api/captures` (`lib/captures/validate.ts`): audio present and at most 10 MB; WebM, MP4/M4A, AAC, MP3 or WAV (Ogg refused, since transcription can't read it); 1 to 95 seconds as reported by the phone (90 s cap plus timer slack); recorded no more than 30 days ago and no more than 5 minutes in the future; a real IANA time zone; latitude and longitude both present or both absent; the capture id a UUID. The hourly limit (`lib/captures/rate-limit.ts`) says when the next note is allowed, for a Retry-After header.
- 2026-10-08: The offline queue tells refusals from failures. 2xx is sent; 408, 429 and 5xx are retried later; any other answer means the server refused the note itself. A refused note is kept on the phone, marked with the server's reason, skipped by later runs and shown on Capture with a Remove button (with a confirmation), so a bad note can't block the ones behind it and nothing is deleted silently.
- 2026-10-08: Export (brief milestone 9) builds CSV and JSON with the same functions the server export will use (`lib/export/people.ts`). CSV: one row per person, times in the zone the person was met in, a byte-order mark so Excel reads Arabic and Thai, CRLF lines, and cells starting with = + - or @ prefixed with an apostrophe so a spreadsheet never runs them as formulas (phone numbers included; Excel hides the apostrophe). JSON: every field, every meeting and its transcript. Recordings and photos aren't included. Phones get the share sheet, computers a download. No contacts-file export, because Ann dropped the research's extra proposals.
- 2026-10-09: Event mode (design concept 7b) built at Ann's request ("proceed with all features"). Start it on Capture with a name; the default is like "Friday evening", and just after midnight still counts as the night before. Each tap of the mic then saves a quick take with no processing screen; it shows "Take 3 saved" and goes straight back to the record button. A banner shows the event and its take count, with End. Ending opens the takes list (`/capture/event`): each take moves through waiting to send, picking out the details, ready, then saved or discarded. "Review next" opens the normal review screen for that take and returns to the list; "Review later" leaves them under "needs review" on Capture. In the mockup the running event and its takes are kept in the browser so they survive the app closing. Real build: an `events` table (one running event per user, migration `20261009000000_events.sql`, checked in PGlite and added to the live RLS test) and `captures.event_id`, with takes going through the normal pipeline. Estimate +4–6 h.
- 2026-10-09: Every new note is written to the phone's queue before it is sent and removed once the server has it, so closing the app mid-upload can't lose it. While that first upload runs, the note is marked with `sendingUntil` (the upload timeout plus 5 s), so a background retry doesn't send it a second time and the "waiting" strip doesn't flash. If the app closed mid-send, the note counts as waiting once that time passes. The queue now runs app-wide (a provider in the app layout), so waiting notes go out from any screen, not only Capture.
- 2026-10-09: The service worker (now v3) also keeps the event takes list offline, so ending an event works without signal; like Capture, its HTML has no personal data.
- 2026-10-09: Sign-in screens (milestone 2) built for real, with a preview mode until Supabase is configured: the forms check what's typed on the server, then open the sample app. Sign in takes a username or email; an unknown username and a wrong password get the same message. Sign-up needs an invite code, which is claimed in one conditional update (`used_at is null`) so two people can't use it at once, and released if account creation fails. Accounts are created by the server with the admin API, already confirmed. That lets the Supabase project turn public sign-up off, so the public key can't be used to skip the invite. Password reset answers the same whether or not the account exists, and its link goes through `/auth/confirm` (token hash, valid one hour). After sign-in the app returns to the page you were going to, but only to paths inside the app.
- 2026-10-09: Every page needs a signed-in user once Supabase is configured, except sign-in, sign-up, password reset, the reset-link handler, the offline page and the MCP connector (which checks its own tokens). Signed-out visitors go to `/login?next=…`; API calls get 401. Before Supabase is configured nothing is protected, so the preview keeps working.
- 2026-10-09: Sign out clears everything the app kept on the phone: the offline copy, notes waiting to send, the running event, and local settings. If notes are still unsent, it asks first. Delete account (milestone 9) removes the user's recordings and photos from storage, then the user, which takes the profile, people, captures, photos and events with it through the foreign keys; the phone is cleared only after that succeeds. Invite links from Settings open sign-up with the code filled in.
- 2026-10-09: Failure, empty and loading states from the design handoff, in a plain first version for design to refine. Review explains a failed step: transcription (the recording is kept and plays, with Try again; Save waits for a name), details not picked out (the transcript opens to type from), or no place name (set the city). The pipeline already reports which step failed (`failedSteps`), now carried on the draft. People and Ask point to recording a first note when nobody is saved, and Ask hides its question box then. Loading placeholders cover People, a profile and the Map. When the server answers 429, the note stays on the phone and a toast says roughly when it goes, from Retry-After. In the preview, `?state=empty` (People, Ask) and `?state=transcription-failed|extraction-failed|place-failed` (Review) show these states; they go when real data arrives.
