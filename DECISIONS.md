- 2026-10-07: The transcript is wrapped in <transcript> tags marked as untrusted data, and any closing tag inside it is stripped. Error text saved on a capture names only the failed step and error type, never note content.
- 2026-10-07: Geocoding runs in parallel with transcription to stay within the 10-second target. Mapbox v6 has no venues, so the stored place is the neighbourhood or street and the venue comes from what the user said.
- 2026-10-07: The extraction system prompt is shorter than Haiku's minimum cacheable prefix, so it isn't marked for prompt caching.
- 2026-10-07: `npm run eval:extraction` runs the 13 sample transcripts against the real model (costs a few cents; needs keys). Vitest configs for unit, integration and eval tests are separate, so each runs only its own files.
- 2026-10-07: Installable app and offline (milestone 8, real build). Manifest opens on Capture in standalone mode, with Home Screen shortcuts for Record a note (`/capture?record=1`, starts recording at once), Scan a card and Ask. `npm run icons` renders every icon (192, 512, maskable 512, Apple 180) from one pin-on-green design, so they never drift apart.
- 2026-10-07: Hand-written service worker (`public/sw.js`), no Workbox or Serwist dependency. It keeps only the shell: Capture, the offline page, and the build files those two pages reference, precached at install so Capture works offline even if it was never opened while the worker was in control. Each online visit to Capture refreshes the offline copy and drops build files from earlier deploys. Pages always come from the network; offline, Capture opens from the copy and other pages show the offline screen. API routes, React Server Component payloads and other pages are never cached. It registers in production only and is served with no-cache so updates arrive on the next visit.
- 2026-10-07: Real-build rule that follows from that: Capture's server-rendered HTML must hold no personal data (drafts and the "needs review" strip load in the browser), because that HTML is kept in the cache. Sign-out clears the caches and, if notes are waiting to send, warns before discarding them.
- 2026-10-07: Recording uses MediaRecorder with the format chosen at runtime: WebM/Opus where supported (Chrome, Android), MP4 otherwise (iPhone Safari), never Ogg; 32 kbps, stopped automatically at 90 seconds. A level meter comes from the live audio, and the screen is kept awake while recording. Where a page can't record (plain HTTP on a LAN address), the mockup simulates instead.
- 2026-10-07: Capture tries the upload first; a failure or a 15-second timeout puts the note in the IndexedDB queue as "waiting to send". `navigator.onLine` is only a shortcut, because a weak signal often reports online while uploads fail. Retries happen when the app opens, comes back online or becomes visible, and every 30 seconds while notes wait and the app is on screen, since a recovering weak signal fires no online event. Still a simple retry, with no Background Sync (brief; iPhone has none). The browser is asked to keep the storage through clean-ups.
- 2026-10-07: Queue runs never overlap (the app opening and coming online can fire together), so a note is never uploaded twice from the phone. `POST /api/captures` will take the capture id from the phone and ignore a repeat (`on conflict (id) do nothing`), so a retry after a timeout that did reach the server can't create a second capture.
- 2026-10-07: Install help (brief §8): a one-line prompt on Capture in phone browsers (not on desktop, not once installed). "How" opens an instruction screen. - 2026-10-08: The product is called King of Names (Ann); "PeopleMap" was the brief’s placeholder. Renamed in the app name, manifest, connector, docs and package name. - 2026-10-08: Real GPS stamp (brief §7.1, research rec. 1). Recording starts `watchPosition` (high accuracy) and keeps the most accurate reading, stopping once it is within 25 m. When recording stops without any fix yet, it waits up to 3 more seconds, then the note goes without a location and the city is set on review. A refused permission doesn't wait at all. The note carries lat, lng and accuracy. Photos and card scans ask for location only when the picture was just taken, starting the request when the camera opens so it is ready by the time the photo is. The Map's Near me, Add person and Met again still use the sample position until the database exists (milestones 3 and 7).
- 2026-10-08: The place name on the recording screen ("Dubai Marina · within 12 m") comes from `POST /api/geocode`, which uses Mapbox's temporary geocoding: it is free up to 100,000 lookups a month, and allowed because the result is only shown. The place that is stored is still looked up with permanent geocoding during processing. Coordinates go in the request body, not the URL, so they stay out of server logs. The route is development-only until sign-in exists; without a Mapbox token the chip says "Location saved".
- 2026-10-08: Upload checks for `POST /api/captures` (`lib/captures/validate.ts`): audio present and at most 10 MB; WebM, MP4/M4A, AAC, MP3 or WAV (Ogg refused, since transcription can't read it); 1 to 95 seconds as reported by the phone (90 s cap plus timer slack); recorded no more than 30 days ago and no more than 5 minutes in the future; a real IANA time zone; latitude and longitude both present or both absent; the capture id a UUID. The hourly limit (`lib/captures/rate-limit.ts`) says when the next note is allowed, for a Retry-After header.
- 2026-10-08: The offline queue tells refusals from failures. 2xx is sent; 408, 429 and 5xx are retried later; any other answer means the server refused the note itself. A refused note is kept on the phone, marked with the server's reason, skipped by later runs and shown on Capture with a Remove button (with a confirmation), so a bad note can't block the ones behind it and nothing is deleted silently.
- 2026-10-08: Export (brief milestone 9) builds CSV and JSON with the same functions the server export will use (`lib/export/people.ts`). CSV: one row per person, times in the zone the person was met in, a byte-order mark so Excel reads Arabic and Thai, CRLF lines, and cells starting with = + - or @ prefixed with an apostrophe so a spreadsheet never runs them as formulas (phone numbers included; Excel hides the apostrophe). JSON: every field, every meeting and its transcript. Recordings and photos aren't included. Phones get the share sheet, computers a download. No contacts-file export, because Ann dropped the research's extra proposals.
- 2026-10-09: Event mode (design concept 7b) built at Ann's request ("proceed with all features"). Start it on Capture with a name; the default is like "Friday evening", and just after midnight still counts as the night before. Each tap of the mic then saves a quick take with no processing screen; it shows "Take 3 saved" and goes straight back to the record button. A banner shows the event and its take count, with End. Ending opens the takes list (`/capture/event`): each take moves through waiting to send, picking out the details, ready, then saved or discarded. "Review next" opens the normal review screen for that take and returns to the list; "Review later" leaves them under "needs review" on Capture. In the mockup the running event and its takes are kept in the browser so they survive the app closing. Real build: an `events` table (one running event per user, migration `20261009000000_events.sql`, checked in PGlite and added to the live RLS test) and `captures.event_id`, with takes going through the normal pipeline. Estimate +4–6 h.
- 2026-10-09: Every new note is written to the phone's queue before it is sent and removed once the server has it, so closing the app mid-upload can't lose it. While that first upload runs, the note is marked with `sendingUntil` (the upload timeout plus 5 s), so a background retry doesn't send it a second time and the "waiting" strip doesn't flash. If the app closed mid-send, the note counts as waiting once that time passes. The queue now runs app-wide (a provider in the app layout), so waiting notes go out from any screen, not only Capture.
